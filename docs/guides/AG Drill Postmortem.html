the main ansible problem

The install step that lied about being done

This is the bug that mattered most: it doesn't stop one drill step, it stops the lab from ever coming up on a fresh VM.

install.yml skipped SQL Server setup because the wrong file was checked

root cause

the problem

install.yml's "already configured" check used stat: path: /var/opt/mssql/mssql.conf and skipped the setup step if that file existed. But the mssql-server RPM creates mssql.conf at package install time — before mssql-conf setup has ever run to accept the EULA and set the SA password.

So on a fresh VM, that file existed the moment the RPM installed, the playbook believed setup was already done, and it silently skipped the one command that actually finishes SQL Server's configuration.

Result: mssql-server crash-looped, with this in the service logs, and the SQL port never opened — wait_for: port 1433 would eventually time out with no useful error pointing at the real cause.

journalctl -u mssql-server
The SQL Server End-User License Agreement (EULA) must be accepted
before SQL Server can start. The EULA can be accepted by running
the setup package again with the parameter --accept-eula...

the fix

Replaced the file-existence check with an actual service-state check:

install.yml
- name: Check whether MSSQL Server is already active and licensed
  command: systemctl is-active mssql-server
  register: mssql_service_active
  failed_when: false
  changed_when: false

and gated the setup step on that instead:

install.yml
when: mssql_service_active.stdout | trim != 'active'

systemctl is-active only returns active once the service is actually up and serving — which can't happen until EULA acceptance and SA password setup have genuinely completed. That's a real signal instead of a proxy that happened to be wrong.

Also bumped the post-setup wait_for timeout from 60s → 120s, since a first-boot mssql-conf setup run on this lab's hardware can take longer than 60s, and a too-short timeout would fail the play even on a run that was actually fine.

before the drill started

Three more fixes already sitting uncommitted

Found while reviewing the working tree before touching anything else. All reviewed, confirmed correct, and committed one at a time.

Concurrent deployments could fight over the same lock

fixed

the problem

Without a guard, calling a second POST /deploy/* while one is still running spawns a fully independent ansible-playbook subprocess against the same hosts. Two concurrent SQL Server RESTORE commands then fight over an exclusive lock and one hangs indefinitely — hit repeatedly during live testing.

the fix

Added is_busy() / _reject_if_busy() — a 409 response whenever a task is already queued or running.

24610e9Reject a new deployment while one is already running

vmnet2 flakiness caused intermittent SSH failures

fixed

the problem

Contacting both VMs at once over the lab's vmnet2 network intermittently produced No route to host — a networking flakiness specific to this VMware Fusion setup, not a code bug.

the fix

ansible.cfg
[defaults]
forks = 1               # one host at a time, no more racing
[ssh_connection]
retries = 5

drill step 2 of 3 — the long one

DR sync-rebuild

This step failed three separate times, for three genuinely different reasons, before it actually worked. Each attempt's failure pointed at the next real cause.

Attempt 1 — a query that could never match

blocking bug

the problem

The final "wait for SYNCHRONIZED" task queried sys.dm_hadr_database_replica_states without scoping it to the local replica. On a 2-replica AG that returns one row per replica — two lines of output, not one:

sqlcmd stdout
NOT SYNCHRONIZING
SYNCHRONIZED

The task's condition did an exact string match against the whole trimmed output:

sync_rebuild.yml
until: (sync_wait.stdout | trim) == 'SYNCHRONIZED'

Two lines glued together can never equal that single word — so the task was mathematically guaranteed to burn through all 30 retries (5 minutes) and fail, regardless of whether vm1 had actually finished syncing.

the fix

Switched to the same robust pattern alwayson.yml already used successfully: count the rows that are not yet synchronized, scoped to this replica specifically, and wait for that count to hit zero.

sync_rebuild.yml
SELECT COUNT(*) FROM sys.dm_hadr_database_replica_states drs
JOIN sys.databases d ON d.database_id = drs.database_id
JOIN sys.availability_replicas ar ON ar.replica_id = drs.replica_id
WHERE d.name = 'AdventureWorks'
  AND ar.replica_server_name = '{{ vmware_name }}'
  AND drs.synchronization_state_desc != 'SYNCHRONIZED'
-- until: (stdout | trim) == '0'

Attempt 2 — a "success" that changed nothing

false positive

the problem

The next run reported failed=0 — but a follow-up independent ag-status check proved nothing had actually changed. vm1 was still reporting itself PRIMARY, byte-for-byte identical to before the run:

ag-status
vm1's own view:
  devops_VM1 PRIMARY HEALTHY / devops_VM2 SECONDARY NOT_HEALTHY
vm2's own view:
  devops_VM1 SECONDARY NOT_HEALTHY / devops_VM2 PRIMARY HEALTHY

Real split-brain. The AG has CLUSTER_TYPE=NONE — no quorum mechanism exists to tell the old primary it's been superseded. Since vm1 stayed reachable through the forced failover, it just kept believing it was still primary the whole time.

The fixed query from attempt 1 reported success anyway because of a genuine gap in its own logic: a primary's own row in that DMV always trivially reports itself as SYNCHRONIZED — a primary is "in sync with itself" by definition. The check could never distinguish "still wrongly primary" from "genuinely fixed."

the fix (first attempt)

Added a pre-check: ask the replica what role it believes it holds, and if it says PRIMARY, force it to step down before anything else runs.

sync_rebuild.yml
ALTER AVAILABILITY GROUP [AG1] SET (ROLE = SECONDARY)
0968a20Detect and resolve split-brain in sync-rebuild before attempting resync

Attempt 3 — the fix itself wasn't a valid command

engine limitation

the problem

That demotion command failed outright:

sqlcmd error
Msg 41104, Level 16, State 5, Server devops_VM1, Line 1
Failover of the availability group 'AG1' to the local replica failed
because the availability group resource did not come online due to
a previous error.

Added three read-only diagnostics to ag_status.yml to investigate properly rather than guess: group-level AG health, a search of the SQL Server error log for AlwaysOn entries, and a direct TCP check of the AG's replication port (5022) between vm1 and vm2 — which ruled out a network partition (the port was reachable both directions).

A web search turned up a Microsoft Q&A thread reporting the identical error on the identical command: ALTER AVAILABILITY GROUP … SET (ROLE = SECONDARY) is undocumented and unsupported for CLUSTER_TYPE=NONE availability groups — it only works on WSFC-clustered AGs. Not a bug in this playbook, and not a transcription error from the source guide either: a real SQL Server engine limitation that the guide's own untested assumption ran into.

The real fix — rebuild the AG instead of patching it

fixed

the fix

Since no in-place fix exists for a cluster-less AG stuck in split-brain, built a new capability instead: POST /deploy/ag-rebuild?authoritative=vm1|vm2. It drops the AG entirely on both replicas, discards the non-authoritative side's stale database, recreates the AG fresh from the authoritative side's current data, and rejoins the other side via automatic seeding — reusing the existing certificate and endpoint from the original build.

Dropping the AG on a replica is normally risky when run against a correctly-self-identified secondary (Microsoft's own docs: it can push the real primary into RESTORING) — but mid-split-brain, both replicas locally believe themselves PRIMARY, so a local drop on either one follows the documented-safe "drop from primary" path from that replica's own point of view.

result

Ran with authoritative=vm2. Both replicas ended up agreeing with each other — proof the split-brain was actually gone, not just hidden:

ansible.log
vm1's view: devops_VM1 SECONDARY HEALTHY
vm2's view: devops_VM1 SECONDARY HEALTHY / devops_VM2 PRIMARY HEALTHY

PLAY RECAP
vm1 : ok=8  changed=3  failed=0
vm2 : ok=9  changed=2  failed=0

AdventureWorks reached SYNCHRONIZED in under 15 seconds via automatic seeding.

drill step 3 of 3

Teardown

Reported clean on the first run — failed=0 on both hosts. It wasn't.

A green PLAY RECAP hid a database that never dropped

false positive

the problem

Buried inside vm1's "Drop AdventureWorks database" task, printed but not raised as a failure:

sqlcmd error
Msg 5052, Level 16, State 1, Server devops_VM1, Line 4
ALTER DATABASE is not permitted while a database is in the Restoring state.
Msg 5069, Level 16, State 1, Server devops_VM1, Line 4
ALTER DATABASE statement failed.

vm1 was the secondary after the AG rebuild, and a secondary's local database sits permanently in a RESTORING redo state — disconnecting it from the AG doesn't bring it online by itself. The drop task's ALTER DATABASE … SET SINGLE_USER step requires an online database, so it refused to run. Ansible still marked the task changed: true anyway, since sqlcmd's exit code doesn't reflect a printed T-SQL error.

(On re-check, the database turned out to already be gone — the batch kept executing past that one failed statement and DROP DATABASE ran anyway. Lucky that time, not something to rely on.)

the fix

Added an explicit state check before the drop, and a recovery step for the case that actually needs it:

teardown.yml
-- if state_desc == 'RESTORING':
RESTORE DATABASE AdventureWorks WITH RECOVERY

Also fixed an adjacent dead check in the same file — a HADR safety-net query referencing a column, is_hadr_enabled, that doesn't exist on sys.databases. Corrected to replica_id IS NOT NULL.

result

Re-ran teardown. Second pass confirmed clean: AG, database, endpoint, certificate, and master key all verified removed from both VMs; MSSQL itself left installed, exactly as teardown.yml is meant to do.

after the drill

Merging with a teammate's parallel work

VS Code's Source Control panel started failing in the background partway through the session: Need to specify how to reconcile divergent branches — and was almost certainly the real source of the repeated .git/index.lock fights all session.

Two people, the same files, no overlap where it counted

resolved

the situation

Local main (13 commits from this session) and origin/main (12 commits from a teammate, merged via GitHub) had split from the same ancestor. The teammate's commits added new MySQL replication and Oracle Data Guard guide docs — and touched several of the same DR files this session had just fixed: failover.yml, sync_rebuild.yml, teardown.yml, deployer.py, deploy.py.

Comparing the diffs first: the teammate's versions of those shared files were consistently earlier, less-developed drafts of the same code — missing the split-brain handling, the RESTORING fix, and the ag-rebuild endpoint. Nothing to lose by keeping ours; nothing to gain by discarding theirs.

the resolution

Merged rather than force-pushed over their work. The merge resolved with zero line conflicts — the changes landed in non-overlapping regions of the shared files despite touching the same filenames. Verified every fix from this session and every new guide doc from the teammate survived intact before committing.

the recurring pattern worth remembering

Three separate times, a clean PLAY RECAP wasn't proof of anything

failed=0 only means Ansible's own modules didn't error — it says nothing about whether a printed SQL error, a trivially-true check, or a command that silently doesn't exist for this configuration actually did what it looked like it did.

  • Sync-rebuild, attempt 2: reported success while vm1 was still in split-brain — the check was trivially true, not actually verifying the fix.
  • Sync-rebuild, attempt 3: the demotion command printed a fatal SQL error but Ansible's changed_when logic never looked at it.
  • Teardown, run 1: a database drop that failed mid-batch was still marked changed: true, because sqlcmd's exit code doesn't reflect a printed T-SQL error.

Every one of these was only caught by reading the actual task output, or by running an independent, unrelated check afterward — not by trusting the recap line.
